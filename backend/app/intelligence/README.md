# Phase 5A: Backend Intelligence Integration Layer

> [!IMPORTANT]
> **Investigative Hypothesis Disclaimer**:
> Outputs generated by this module are **investigative leads and candidate structural associations**, NOT legal evidence, factual determinations of identity, or proof of criminal activity. All predictions serve to assist human investigators in prioritizing exploratory hypothesis verification.

---

## 1. Overview & Architecture

The **Intelligence Integration Layer** (`backend/app/intelligence/`) bridges the offline GraphSAGE machine learning pipeline (Phase 4) and the live FastAPI investigation platform (Phase 5).

```
Phase 3 Knowledge Graph ───┐
(nodes.csv, edges.csv)     │
                           ▼
Phase 4 GraphSAGE Outputs ───► [Phase4ArtifactAdapter]
(predictions.csv, etc.)            │ (Zero Ground-Truth Ingestion)
                                   ▼
                            [LeadRepository] (In-Memory Cache & Filtering)
                                   │
                                   ▼
                         [FastAPI Intelligence Router] (/api/v1/intelligence/*)
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       ▼                                                       ▼
[JWT & RBAC Auth Check]                                [Case Clearance Enforcement]
```

---

## 2. Phase 4 Artifact Ingestion & Zero-Leakage Guarantee

The adapter reads frozen artifacts from `output/graphsage/`:
- `predictions.csv`: 2,332 scored pairs between `PERSON ↔ PERSON` (and provisional resolved entities).
- `candidate_links.csv`: Candidate pair metadata (cases, cross-case flags, negative categories).
- `node_embeddings.csv`: 32-dimensional inductive GraphSAGE node representations.
- `output/graph_analysis/edges.csv`: Evidence-backed edges providing concrete provenance records.

### Strict Ground-Truth Isolation
- The `label` column in Phase 4 CSVs is an offline benchmark ground-truth artifact.
- **The Phase 4 Adapter statically ignores and drops the `label` field.**
- Ground-truth values are never loaded into memory, never serialized into Pydantic models, and never returned in API responses.

## 3. Investigation Lead Schema

The internal and API data structure is represented by `InvestigationLead`:

| Field | Type | Description |
| :--- | :--- | :--- |
| `lead_id` | `str` | Deterministic hash identifier (e.g. `LEAD_7F3A2B9C0E1D`) |
| `source_entity` | `str` | Observational entity identifier |
| `target_entity` | `str` | Observational entity identifier |
| `source_case_ids` | `List[str]` | Case dossiers containing source entity |
| `target_case_ids` | `List[str]` | Case dossiers containing target entity |
| `is_cross_case` | `bool` | True if entities appear across distinct case files |
| `confidence` | `float` | Model prediction score ($0.0 \le p \le 1.0$) |
| `priority` | `PriorityTier` | Deterministic priority tier (`HIGH`, `REVIEW`, `LOW`) |
| `prediction_type` | `PredictionType` | Neutral type ("Potential Association", "Candidate Link") |
| `evidence_strength` | `EvidenceStrength`| Corroboration classification (`STRONG`, `MODERATE`, `WEAK`) |
| `explanation` | `str` | Plain-English non-prejudicial summary |
| `supporting_modalities` | `List[str]` | Evidence types (e.g. `DEVICE`, `LOCATION`, `PERSON`, `VEHICLE`) |
| `common_intermediates` | `List[str]` | Representative 2-hop topological intermediate nodes |
| `caveats` | `List[str]` | Investigative warnings (e.g. public Wi-Fi or transit bus markers) |
| `supporting_records` | `List[Record]`| Concrete observable evidence records with real provenance |
| `created_at` | `str` | ISO UTC timestamp |

## 4. Priority Logic & Hard-Negative Defense

Priority classification uses a deterministic policy respecting Phase 4 thresholds and structured hard-negative suppression:

1. **Threshold Tiers**:
   - `HIGH`: Confidence $\ge 0.70$
   - `REVIEW`: $0.40 \le$ Confidence $< 0.70$
   - `LOW`: Confidence $< 0.40$
2. **Public Infrastructure Safeguard**:
   - Pairs classified under Phase 4 hard-negative categories (`NEG_D_SHARED_LOCATION`, `NEG_E_SHARED_COMMERCIAL_VEHICLE`, `NEG_F_SHARED_PUBLIC_IP`, `NEG_G_HIGH_DEGREE_HUB`) or sharing confirmed public infrastructure (Wi-Fi IP `103.21.244.18`, sleeper bus `VEH_026`, generic transit cities) are **automatically capped at `LOW` priority**.
   - Public infrastructure alone cannot trigger a `HIGH` or `REVIEW` priority lead.

## 5. Explanation Engine (Deterministic, No LLM)

Every explanation is synthesized deterministically from actual graph topology and observable evidence tables.
- **Narrative Explanation**: Outlines intermediate count, modalities, cross-case nature, and caveats.
- **Structured Evidence Records**: Contains authentic provenance:
  ```json
  {
    "reason": "Direct observational association with shared intermediate VEH_028",
    "evidence_type": "USED_DEVICE",
    "case_id": "CASE_009",
    "record_id": "DEV_016_865048881437918",
    "source_file": "device_logs.csv",
    "source_row": null,
    "timestamp": "2025-07-11 05:44:00"
  }
  ```
- If a provenance field is unavailable, the engine returns `null` rather than inventing data. Zero hallucinated fields.

## 6. Security, RBAC & Case Authorization

- **Authentication**: Integrates with existing JWT bearer authentication (`app.core.security.get_current_user`).
- **Role-Based Access**:
  - `ADMIN` & `SUPERVISOR`: Global clearance across all case files and leads.
  - `INVESTIGATOR` & `ANALYST`: Scoped clearance. Users can only query leads from case files to which they are actively assigned via `CaseMember`.
- **Case Clearance Check**:
  - `GET /api/v1/intelligence/leads?case_id=CASE_007`: If the user lacks access to `CASE_007`, the endpoint immediately returns `403 Forbidden`.
  - Single lead view (`/leads/{lead_id}`): If the user lacks access to both source and target cases, returns `403 Forbidden`.

## 7. API Endpoints

All endpoints are registered under `/api/v1/intelligence/` and require valid JWT Bearer authentication.

| Method | Endpoint | Query Parameters | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/v1/intelligence/leads` | `case_id`, `min_confidence`, `priority`, `is_cross_case`, `limit`, `offset` | Paginated, filterable candidate association leads |
| `GET` | `/api/v1/intelligence/leads/{lead_id}` | None | Detailed lead by ID |
| `GET` | `/api/v1/intelligence/leads/{lead_id}/evidence`| None | Provenance records supporting a specific lead |
| `GET` | `/api/v1/intelligence/cross-case` | `min_confidence`, `priority`, `limit`, `offset` | Cross-case potential associations summary |

## 8. Limitations & Investigator Advisory

1. **Topological Inference**: GraphSAGE embeddings reflect structural connectivity within evidence dossiers; they do not account for external real-world context not present in evidence records.
2. **Provisional Entities**: Associations involving `PROV_RES_ENT_xxx` rely on Entity Resolution clustering probabilities and require corroborating forensic evidence.
3. **Legal Classification**: Leads do not establish criminal complicity, guilt, or legal culpability.
